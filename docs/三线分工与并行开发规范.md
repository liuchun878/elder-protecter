Team4 ｜ 版本 v2（机器人 / 场景 / 人）｜ 2026-10-02
依据：[契约-接口.md](../契约-接口.md)、[仿真呈现与开发阶段计划.md](../仿真呈现与开发阶段计划.md)、调研报告 v2 第 08 章

## 0 · 分工结论

| 线 | 一句话 | 拿什么 | 建议谁拿 |
|---|---|---|---|
| **R** 机器人线 | 让机器人会动、会说话 | 机器人本体 + 路径动画 + 长者端面板 + 提示通道（语音 / 大字 / 低频音 / 灯） | 想做机器人的队员 |
| **S** 场景线 | 让世界看得见、让集成不出乱 | 房间 / 相机 / 光照 / 性能 + **演示时钟** + 装配 `main.js` + 集成门禁 + 录屏 + 演示操作 | 想做场景的队员 |
| **H** 人线 | 让这件事真的成立 | **王阿姨（3D 人形 + 人的状态与行为）** + 服药计划 + 事件状态机 + 记录 + 升级链路 + 家属端 + 契约 + 陈述脚本 | **队长** |

**这一刀好在哪**：三条线各自对应一个**角色**（机器人 / 环境 / 人），而不是三个技术层。演示里"人"是可见的主体，这正好支撑答辩的核心论点——最大风险是「老人觉得这是给子女用的监控」，而我们的演示里老人是主角，不是被监视的对象。

**但这一刀有一个必须堵的洞**（报告第 08 章点名警告的失败模式）：按角色切，很容易**没人拥有闭环**——机器人走完、场景画完、人摆完，最后没人写「药到底拿没拿、没拿怎么通知家属」。所以闭环**按环节显式落到三条线**，见第 1 节。不留无主环节。

## 1 · 闭环责任矩阵（堵洞的地方）

每个环节都有主责人。**"主责"意味着坏了就找他，不是"也参与了"。**

| # | 闭环环节 | 内容 | 主责 | 协作 |
|---|---|---|---|---|
| 1 | 计划 | 服药计划录入 / 变更 / 有效期 / 暂停不删 | **H** | — |
| 2 | 时间 | 演示时钟、加速、复位 | **S** | H（到点判定读它） |
| 3 | 到点判定 | 计划时段 × 时钟 × 人在不在 × 安静时段 → 触发或 `defer` | **H** | S（时钟） |
| 4 | 送达 | 机器人走到人的位置、药盘抬升 | **R** | S（位置与相机）、H（`activeEventId`） |
| 5 | 提示 | 语音 + 大字 + 低频音 + 灯；首次未响应**换通道 + 换措辞 + 拉长间隔** | **R** | H（事件状态） |
| 6 | 取药确认 | 一键确认、防重复、状态写回 | **H** | R（确认按钮在长者端面板上） |
| 7 | 记录 | 追加式日志 + **双时间戳** + 导出 | **H** | — |
| 8 | 升级 | T+60s 重试、T+180s 通知家属、冷却去重、只推事实 | **H** | R（重试时的机器人行为） |
| 9 | 家属闭环 | 通知、三选项、「已知情未服」、时间线 | **H** | — |
| 10 | 装配与门禁 | `main.js`、双屏调度、每里程碑合并、录屏兜底 | **S** | 全员 |
| 11 | 陈述 | 60 秒 / 5 分钟脚本（H 起草）、**主讲（R）**、演示操作（S） | **R** 主讲 | H 起草、S 操作 |

**如果两天里只能保一件事：保 H 线的第 3、6、7、8 节。** 机器人可以变成一个方块、房间可以变成几个色块，但「到点 → 确认 → 记录 → 没确认就升级」不能没有——那是产品的本体。

## 2 · 闭环怎么"交棒"（三条线之间的接口时点）

并行开发最容易死在"等我把逻辑写完"。所以交棒点必须显式：

```
S: clock.js  ──演示时钟──▶  H: schedule.js ──到点触发──▶  写入 events 状态
                                                            │
R: robot.js  ◀──activeEventId + presence.location───────────┘
   走到人身边、药盘抬升、语音/大字/灯提示
        │
        ▼  老人取走
H: machine.confirm()  ──▶  log.js 写双时间戳 ──▶ 状态 confirmed
        │
        └─ 没取走 ──▶ R 换通道重试 ──▶ H: escalate.js 通知家属（只推事实）
```

三条线**只通过 `契约-接口.md` 通信**（`store.getState()` 读、命令函数写）。谁都不 import 别人的文件。

## 3 · 文件归属（独占所有权，这是不冲突的根本）

**一个文件只有一个人改。** 要改别人的文件：在 PR 里说明并让 owner 改，或 owner 明确同意后在同分支改。

| 线 | 文件 |
|---|---|
| **R** | `prototype/js/robot.js`（本体 + 行为动画）、`prototype/js/hud.js`（长者端面板 = 机器人的脸和嘴）、`prototype/js/audio.js`（语音 + 低频音 + 灯效）、`prototype/index.html`、`prototype/css/**` |
| **S** | `prototype/js/scene3d.js`、`prototype/js/room.js`、`prototype/js/scene2d.js`（降级）、`prototype/js/clock.js`（演示时钟）、`prototype/js/main.js`（装配）、`prototype/vendor/**`、`scripts/**`、`.github/**`、`CODEOWNERS`、`recordings/**`、`docs/演示机预检.md` |
| **H** | `prototype/js/person.js`（人形 + 人的位置与状态）、`prototype/js/plan.js`、`prototype/js/presence.js`、`prototype/js/schedule.js`、`prototype/js/machine.js`、`prototype/js/log.js`、`prototype/js/escalate.js`、`prototype/js/family.js`（家属端）、`prototype/js/store.js`、`契约-接口.md`、`plan/tasks.yaml`、`STATUS.md`、`docs/演示脚本.md`、`docs/简报卡.md` |
| **公共** | `README.md`、`CHANGELOG.md`、`AGENTS.md`（改动需在 PR 里说明） |

**两条铁律**：

1. **依赖单向**：`H（数据与状态）← R / S（表现与装配）`。H 永远不 import R、S 的文件。这正是 3D 能整体降级为 2D 而不动功能层的原因。
2. **只有一个人写业务状态机**：`machine.js` 归 H。R 的机器人行为是 **`store` 状态的纯函数**（状态变 → 目标位置/动画变），不许自己再写一套状态机——两套状态机必然漂移。

**两个共享文件先一次性说清**：

- `prototype/index.html`（**R**）：R 在 D1 上午一次性留出 `<canvas id="scene">` 与 `<div id="hud">` 挂载点，**此后 S 不再改 index.html**。
- `prototype/js/main.js`（**S**）：只做装配——`store.subscribe()` → 调 `hud.render(state)` / `scene.render(state)` / `person.render(state)`。**不写任何业务规则。**
- `person.js`（**H**）要往 3D 场景里放人形，通过契约里的 `scene.addActor(obj3d)` / `scene.setActorPosition(id, location)`（由 S 提供）。

## 4 · 三个人的四个半天块（每人 4 块，共 12 块）

一块 = 一个半天 ≈ 4 小时。每块都有**可见产出**与**验收**。

### R · 机器人线

| 块 | 做什么 | 产出 | 验收 |
|---|---|---|---|
| D1 上 | 读契约；`index.html` + CSS 叠层骨架 + 适老化硬数值（对比度、字号、点击目标 ≥60×60）；留 `#scene` / `#hud` 挂载点 | 页面骨架 + 叠层样式 | 投屏 100% 缩放下大字不裁切；对比度 ≥4.5:1 |
| D1 下 | `robot.js`：几何体拼机器人（底盘 + 机身 + 药盘 + 发光环）；药盘抬升；**状态 → 位置/动画的纯函数** | 机器人能被 `main.js` 驱动 | 改 `presence.location`，机器人走到正确位置 |
| D2 上 | 路径动画（充电座 → 客厅 → 卧室 → 餐桌）、缓动、到点朝向、约 1.2 m/s；提示时的机器人动作 | 送达动作完整可见 | 从到点走到人到位的动作连贯，无穿模 |
| D2 下 | `hud.js` + `audio.js`：大字面板、药格灯、低频提示音、语音 `speechSynthesis` + 预录音频兜底、一键确认 + 防重复；适老化走查 | 长者端完整交互 | 走查清单全项或登记偏差 |

**最先砍**：发光环与状态细节 → 保留药盘抬升与行走 → 再砍到单个方块（**功能不受影响**）。

### S · 场景线

| 块 | 做什么 | 产出 | 验收 |
|---|---|---|---|
| D1 上 | 读契约；`scene3d.js` 骨架（renderer / camera / 循环 / resize）+ **WebGL 检测与 2D 降级入口**；vendor Three.js 两个文件 + **断网验证** | 页面能渲染空场景；断网可加载 | 断网刷新完整加载；Network 面板零外部请求 |
| D1 下 | `room.js` 房间与分区（客厅 / 卧室 / 餐桌·厨房台面）+ 相机光照；`clock.js` 演示时钟（1 / 60× / 600×、直接设时钟、复位） | 房间可见、时钟可驱动 | 推进时钟能触发 H 的到点判定 |
| D2 上 | `main.js` 装配与订阅；调试抽屉（时间 / 在场 / 离线 / 复位）；`scene.addActor` / `setActorPosition` 给 H 用；`family.js` 的双屏调度 | 三块屏都能跑起来 | H 的人形能出现在正确位置；副屏可操作 |
| D2 下 | 性能与适配（pixelRatio 上限 2、关阴影、≥30 FPS）；**执行集成门禁**；录屏兜底（三场景 + 加速版）；演示机预检 | 录屏齐备 + 门禁结论 | 连排可用；三场景录屏各一条 |

**最先砍**：家具细节 → 降为分区色块；特写机位 → 不要；2D 降级 → 只留"色块房间 + 移动方块"极简版。

### H · 人线（队长）

| 块 | 做什么 | 产出 | 验收 |
|---|---|---|---|
| **D1 上** | **第一件事不是写完整逻辑**：把契约 §3 的**命令接口空实现**提交上去（函数存在、签名正确、返回合法默认值）；然后 `store.js` + `plan.js` | R、S 可立即开工 | `store.getState/subscribe` 可用；计划可增删改、可置 `paused` |
| D1 下 | `presence.js`（在家 / 客厅 / 卧室 / 出门 / 安静时段）+ `schedule.js`（到点判定）+ `person.js`（3D 人形 + 位置与姿态） | 到点能产生事件；人出现在场景里 | 推进时钟触发 `notifying`；切换位置人形跟着动 |
| D2 上 | `machine.js` 事件状态机 + 异常分支；`log.js` 双时间戳 + 导出 | 场景 1 闭环完整 | 按验收脚本 5 步全过；重复取药被拦截 |
| D2 下 | `escalate.js`（T+60s 换通道换措辞、T+180s 家属通知、冷却去重、「稍后再说」、`skipped_known`、时间线数据）+ `family.js` 家属端（计划变更 / 通知三选项 / 时间线）；**脚本定稿** | 场景 2、3 完整 | 升级在加速档 60 秒内完成；通知**零补服建议** |

**最先砍**：时间线回放 → 列表 + JSON 导出；冷却合并 → 只做单条去重；家属端 → 只留"计划变更 + 通知三选项"两个视图。

### 工作量是"有意过载"的

三条线各约 16–18 小时，两天可用约 15–16 小时/人，**整体超约 10%**。这是刻意留的取舍空间，由每人的"最先砍"清单释放。**不要靠加班补，要靠砍。**

## 5 · 里程碑与合并（每个里程碑合并一次）

里程碑沿用 [仿真呈现与开发阶段计划.md](../仿真呈现与开发阶段计划.md) 第 3.1 节：
`p0-baseline` → `p0.5-parallel-ready` → `p1-contract-scene` → `p2-happy-path` → `p3-escalation` / `p4-plan-change` → `p5-frozen` → `p6-demo`

### 5.1 分支

| 项 | 约定 |
|---|---|
| 主干 | `main` —— **只接受里程碑合并**，不直接提交 |
| 个人分支 | `feat/r-<主题>`、`feat/s-<主题>`、`feat/h-<主题>`（例：`feat/r-robot-anim`、`feat/s-room`、`feat/h-machine`） |
| 契约分支 | `contract/<主题>` —— 只改 `契约-接口.md`，必须另外两人 review |

每天收盘前：**各自 rebase `main` 并推送自己的分支**，禁止留过夜不同步。

### 5.2 合并顺序（固定，不临场商量）

```
H（数据与状态） → R（机器人 + 长者端面板） → S（场景 + 装配）
```

理由：依赖单向——S 的 `main.js` 依赖 H 的 store 与 R 的 hud，所以装配层最后合。**H 先合**能让 R、S 立刻 rebase 到稳定的命令实现上。

### 5.3 里程碑完成定义（DoD，7 条）

1. 该里程碑功能验收通过（第 4 节各块"验收"列）
2. `CHANGELOG.md` 增加一段，与里程碑 tag 对应
3. `STATUS.md` 与 `plan/tasks.yaml` 状态更新
4. **断网可跑**（离线红线）
5. 仓库内**无凭据、无真实个人信息**
6. 三线均已 rebase 并合入 `main`
7. 打 annotated tag + `git push origin main --tags`

**门禁执行人 = S**；**契约变更必须由 H 发起**——两者分开，避免自己验自己。

### 5.4 冲突处理

- "文件独占"已把冲突率压到接近零。仍出现冲突：**由该文件 owner 解决**，另一方不自行决定。
- 契约相关冲突：以 `契约-接口.md` 为准——先把契约改对，再改实现。
- 一旦发现两人改了同一个文件：**立即停止该文件的并行修改**，owner 收口后再继续。

## 6 · 交叉验证环（谁验谁，禁止自我验证）

```
H 的产出 ←── R 验        R 的产出 ←── S 验        S 的产出 ←── H 验
```

| 里程碑 | 作者自测 | 交叉验证人 | 具体验什么 | 门禁执行 |
|---|---|---|---|---|
| P1 契约 + 骨架 | 各自 | R↔S↔H | H 验契约自洽；R 验 S 的离线加载；S 验 R 的叠层对比度 | S |
| P2 主链路 | H | **R 按验收脚本重放场景 1** | 不许 H 自己点给自己看 | S |
| P3 升级链路 | H | **S 重放场景 3** | 重点：通知文本**有没有补服建议** | S |
| P4 方案变更 | H | **R 验家属端** | 是否只调契约命令、有没有绕过 `store` | S |
| 3D 场景 | S | **H 验** | 位置/时钟是否与人的状态一致 | S |
| 机器人行为 | R | **S 验** | 集成后 状态→动画 是否对得上 | S |
| P5 冻结 | — | 三人一起 | 适老化清单 + 断网演练 | S |
| P6 演示 | — | 三人轮流操作一次 | 连排 3 次 | S |

**「按脚本重放」是硬要求，由非作者执行。** 这也是报告里 A 角色「演示与清晰度」职责的落地方式——讲不清，往往是实现者自己觉得"这很明显"。

## 7 · 每日节奏与第一个同步点

| 时间 | 事项 | 时长 |
|---|---|---|
| 09:00 | 早对齐：今天各块目标 + 阻塞项 | 15 分钟 |
| 13:00 | 午间检查点：上半天产出是否达成；**未达成当场决定砍什么** | 15 分钟 |
| 17:30 | 晚验收：逐条验当天验收点；**各自 rebase `main`** | 30 分钟 |

**关键的第一个同步点**：H 在 Day 1 上午必须**先提交命令接口的空实现**。否则 R、S 会在整个上午空等——并行开发最容易被"等我先把逻辑写完"这一句话拖垮。

**契约冻结**：Day 1 11:00。之前三人一起 review 一次；之后只允许"加字段 / 加函数"，不允许改语义。

**卡住规则**：任何人卡住超过 30 分钟必须在群里说，不要自己扛到晚上。

## 8 · 谁主讲（一条容易犯的错）

| 职责 | 归谁 | 理由 |
|---|---|---|
| 60 秒 / 5 分钟脚本**起草** | **H** | 故事讲的是"人"，H 拥有演示的情节与转折（不理睬 / 出门 / 家属处置） |
| **主讲与答辩** | **R** | 机器人是"一句话讲清"的视觉锚点；R 是三条线里负担最轻的（约 15h），连排 3 次不会挤掉关键路径 |
| 演示操作 | **S** | 主讲不能自己操作——一边翻页一边点按钮必然出错 |

**规则**：**主讲不兼任演示操作，主讲也不承担关键路径的最后一块。** 如果 R 确实是最会表达的人，就把主讲给他；如果他怯场，换 H 讲、把脚本交给 R——但"主讲 ≠ 操作"这条不变。

## 9 · GitHub 设置（队长操作）

### 9.1 建主仓并首推

```bash
cd <仓库根目录>
git remote add origin https://github.com/liuchun878/elder-protecter.git
git push -u origin main --tags
```

### 9.2 邀请两位队员

- 网页：仓库 → **Settings → Collaborators → Add people** → 输入对方 GitHub 用户名或邮箱 → **Write** 权限
- 或 `gh`：`gh api -X PUT repos/liuchun878/elder-protecter/collaborators/<对方handle> -f permission=push`

**邀请后把 `CODEOWNERS` 里的占位 handle 换成真实用户名**（三个人），否则 GitHub 不会自动请求对应 owner review。

### 9.3 保护 `main`

仓库 → **Settings → Branches → Add branch ruleset**（或 classic protection），针对 `main`：

- ☑ Require a pull request before merging
- ☑ Require approvals：**1**（两天三人，别设 2，会拖死节奏）
- ☑ Require branches to be up to date before merging
- ☐ 不开 Require status checks（两天内不搭 CI）

或：

```bash
gh api -X PUT repos/liuchun878/elder-protecter/branches/main/protection \
  -H "Accept: application/vnd.github+json" \
  -f "required_pull_request_reviews[required_approving_review_count]=1" \
  -F "required_status_checks=null" -F "enforce_admins=false" -F "restrictions=null"
```

### 9.4 PR 流程

1. 推个人分支 → 网页开 PR（模板 `.github/pull_request_template.md`）
2. 指派另外两人中至少 1 人 review（`CODEOWNERS` 自动建议）
3. PR 里贴该块验收结论（跑了什么、看到什么）
4. 合并顺序按第 5.2 节，S 执行门禁

### 9.5 GitHub Milestones（可选）
